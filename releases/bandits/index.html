Recommendation with multi-armed bandits

Learning which video to show from logged feedback alone, and measuring when knowing the user starts to pay.

github.com/hajar6883/bandits-online-allocation

The constraint

A recommender has to choose what to show before it knows what anybody likes. Every slot spent on an unknown video is a slot not spent on one that already works, and every slot spent on the safe choice is a video you never learn about. That is the explore/exploit trade-off, and it is the whole problem.

The harder part is evaluation. A policy that wants to show video 42 to a user who never saw it has no reward to collect from an ordinary log. KuaiRec is the exception: in its small matrix nearly every user was shown nearly every video, so the logged answer exists for almost any choice a policy makes.

How it works

  KuaiRec interaction log        4.7M rows
        |
        v
   prepare     join users + items, sub-sample to 135 users x 85 videos,
                drop leakage columns
        |
        v
   featurise   reward = 1 if watch_ratio > 0.8
                arm = video (85), context = 23 user features + intercept
        |
        v
   evaluate    5 policies x 5,000 rounds x 50 trials, replayed on the log
        |
        v
   results  ·  reward curves  ·  arm frequencies

Five policies, split by whether they look at who the user is:

  • Non-contextual — epsilon-greedy, UCB1, Thompson Sampling. Video 42 is good or bad, full stop.
  • Contextual — LinUCB, Linear Thompson Sampling. Video 42 may suit this user and not the next.

Every policy is evaluated the same way: a user arrives, the policy picks a video for that user, and the reward is what that user actually did with that video in the log. A contextual policy sees the user's features before choosing; a non-contextual one does not. For the 6% of pairs with no log, the event is discarded and another user is drawn. No simulator, no model inventing counterfactuals.

The whole thing runs as a Dataiku DSS Flow: three Python recipes, a scenario that force-rebuilds the chain from raw data, and a dashboard comparing the policies.

Evidence

  • Early on, context costs more than it pays. Over the first 500 rounds epsilon-greedy scores 0.791 and LinUCB 0.725: LinUCB has 24 parameters to learn per video, epsilon-greedy has one.
  • With enough feedback, LinUCB passes the ceiling of any non-contextual policy. Over the last 500 of 5,000 rounds it reaches 0.966, against 0.915 for the single best video shown to everyone and 0.889 for Thompson Sampling. A video picked at random scores 0.508.
  • The gain does not transfer to new users. A per-video model on the same features, scored on held-out users, is worth 0.815, below the single best video. With 135 users, LinUCB mostly learns the tastes of the same users coming back.
  • Averaged over all 5,000 rounds: epsilon-greedy 0.854, Thompson Sampling 0.849, LinUCB 0.808, UCB1 0.794, Linear Thompson Sampling 0.693. Exploration parameters were set once, not tuned.
  • The port to Dataiku runs the same code: the policy files are byte-identical to the scripts' and, with a shared seed, the recipe reproduces the scripts' numbers exactly.
  • A correction: an earlier version of this page reported LinUCB at 0.918 against 0.778. LinUCB was reading one fixed context per video, so it never saw different users. The evaluation was rewritten so that all five policies face the same stream of users.
